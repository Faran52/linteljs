# Contributing

This is a pnpm workspace of three published packages, so a change here reaches somebody else's project.

## What you need

Node 26.10.0 or newer, and pnpm 12.6 or newer. Both are declared in `engines`, so an older one fails at
install rather than halfway through a run.

```
pnpm install
pnpm mod-types
pnpm check
```

`pnpm mod-types` has Claude Code write its plugin API declarations beside the two mods (the shipped
check band and `.claude/skills/linteljs/`); it loads each with `claude -p /cost --plugin-dir <dir>`,
a local command, so no model is called. `typecheck` checks the mods against them and fails when they
are missing or older than the engine `scripts/typecheck-mods/constants.ts` pins; rerun it after
updating Claude Code. In CI, where no Claude Code runs, the mods' typecheck is skipped.

`pnpm check` is the gate: `build`, `lint`, `lint:types`, `lint:starters`, `lint:css`, `typecheck`,
`test:coverage`. A project generated by `@linteljs/create` receives the same legs less `lint:starters`,
and it has to be green before a change is finished. Coverage is gated at 100% on statements, branches,
functions and lines; a line that cannot be reached is deleted rather than ignored.

The end-to-end suite is separate, because it generates 185 real projects over the network, installs
each and runs its gate. `E2E_PM` narrows it to one package manager's cases, and `-t '<label>$'` to one
case:

```
E2E_PM=pnpm pnpm --filter @linteljs/create test:e2e
```

Run it for anything that changes what a generated project receives: it sees what the unit gate
cannot, such as a package that installs but is never imported.

`pnpm lint:starters`, a leg of `pnpm check`, lints the starter source. It writes the cases that between them
carry every starter text into real projects under `~/.cache/linteljs/typed/`, installs them against this
checkout's packed config and plugin, and runs each project's own `eslint . --max-warnings 0`, type-aware rules
included. It lints only the cases whose generated tree changed since their last clean lint; `--all` lints every
one, as CI does. The first run installs everything and takes several minutes; a run with nothing changed takes
under one. It needs the network. `pnpm lint:starters:fix` writes autofixes back to the templates.

## The three packages

```
eslint-plugin  <-  eslint-config  <-  create
   the rules        the layers        the scaffolder
```

The direction is one way and enforced. `create` never imports `eslint-config` at runtime; it writes
the package name into text, which is why it can be built and tested before that package publishes.

- **`packages/eslint-plugin`** is the rules. One directory per rule, named for its id, holding the
  rule named for its export, its test beside it, `README.md`, and a `utils/` directory where the rule
  has private helpers. Adding one is the `add-eslint-rule` skill,
  `.claude/skills/add-eslint-rule/SKILL.md`.
- **`packages/eslint-config`** is the flat config layers. One directory per layer under `layers/`,
  `frameworks/` or `libraries/`, holding an entry named for it with the group's suffix
  (`frameworks/react/reactFramework.ts` exports `react`) and its test beside it.
  `compose-config/composeConfig.ts` composes them and owns the ordering.
- **`packages/create`** is the scaffolder, in rings listed once in `src/rings.ts`: `answers/`,
  `config/`, `targets/` and `utils/` inside, `emitters/` turning answers into file text, and
  `disk/`, `spawns/`, `terminal/` and `pipeline/` outside. The direction points inward only,
  enforced by `import-x/no-restricted-paths`.

## Where the reasons live

`docs/DESIGN.md` holds the decisions that are not visible in the code, including the non-goals. Read it
before re-adding something it rules out; its contents list says which of its three audiences you are.

The two `CLAUDE.md` files are the working rules for this repository, written for an agent but
accurate for a person. `.claude/rules/` adopts the standard this repository publishes, from
`packages/create/templates/fragments/claude-rules/`, and records where it differs.

## Tests

A change to a rule or a fixer needs a case in that rule's own suite. A change to what a fixer emits
also needs an entry in `packages/eslint-plugin/__mocks__/fixerSamples.ts`, a corpus run against
every rule, so one nasty input covers all of them.

Prove a new test can fail. Break the code, watch it go red, revert. A test added beside a fix that
still passes with the fix reverted has pinned nothing.

## Commits

Conventional commits, and no trailers: no `Co-Authored-By`, no tool footer, whatever your editor
suggests by default. Stage your own files by path.

In Claude Code the shipped hooks run here too: a commit is held until `pnpm check` has passed on
the work tree, run on its own or redirected to a file outside it, never piped or chained, and a
dependency change asks you first. `.claude/skills/linteljs/` adds the repo's own guards and bands.

No em-dashes anywhere: not in code comments, JSDoc, documentation, commit messages or rule
descriptions.

## Releasing

Maintainers only, and it is one push. Bump the three package versions and the two constants that
mirror them, then push a branch named for the version. `docs/DESIGN.md` has the whole ritual and the
reasons behind it.
