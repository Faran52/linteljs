# Contributing

This is a pnpm workspace of three published packages. Everything in it is outward facing, so a
change here reaches somebody else's project.

## What you need

Node 24.19 or newer, and pnpm 11. Both are declared in `engines`, so an older one fails at install
rather than halfway through a run.

```
pnpm install
pnpm check
```

`pnpm check` is the gate: `lint`, `lint:css`, `typecheck`, `test:coverage`, `build`. It is the same
chain a project generated by `@linteljs/create` receives, and it has to be green before a change is
finished. Coverage is gated at 100% on statements, branches, functions and lines; a line that
cannot be reached is deleted rather than ignored.

The end-to-end suite is separate, because it scaffolds nine real projects over the network and
takes about five minutes:

```
pnpm --filter @linteljs/create test:e2e
```

Run it for anything that changes what a generated project receives. It has caught defects the unit
gate structurally cannot see, including a package that installs but is never imported and a first
`pnpm install` that aborts.

## The three packages

```
eslint-plugin  <-  eslint-config  <-  create
   the rules        the layers        the scaffolder
```

The direction is one way and enforced. `create` never imports `eslint-config` at runtime; it writes
the package name into text, which is why it can be built and tested before that package publishes.

- **`packages/eslint-plugin`** is the rules. One directory per rule, named for its id, holding
  `index.ts`, `index.test.ts` and `README.md`. Adding one has six steps, and they are listed in that
  package's own `CLAUDE.md`.
- **`packages/eslint-config`** is the flat config layers. One file per layer, named for its single
  export. `defineConfig.ts` composes them and owns the ordering.
- **`packages/create`** is the scaffolder, in three rings: `model/` is what the user chose,
  `artifacts/` turns answers into file text, `run/` touches disk and argv. The direction points
  inward only, enforced by `import-x/no-restricted-paths`.

## Where the reasons live

`DESIGN.md` holds the decisions that are not visible in the code, including the non-goals. Read it
before re-adding something it rules out; its contents list says which of its three parts you want.

The two `CLAUDE.md` files are the working rules for this repository, written for an agent but
accurate for a person. `.claude/rules/` holds the standard this repository publishes and adopts for
itself, and records where it differs.

## Tests

A change to a rule or a fixer needs a case in that rule's own suite. A change to what a fixer emits
also needs an entry in `packages/eslint-plugin/__mocks__/fixerSamples.ts`, a corpus run against
every rule, so one nasty input covers all of them.

Prove a new test can fail. Break the code, watch it go red, revert. A test added beside a fix that
still passes with the fix reverted has pinned nothing.

## Commits

Conventional commits, and no trailers: no `Co-Authored-By`, no tool footer, whatever your editor
suggests by default. Stage your own files by path.

No em-dashes anywhere: not in code comments, JSDoc, documentation, commit messages or rule
descriptions.

## Releasing

Maintainers only, and it is one push. Bump the three package versions and the two constants that
mirror them, then push a branch named for the version. `DESIGN.md` has the whole ritual and the
reasons behind it.
